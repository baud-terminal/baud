1. Where fd 0/1/2 point for a LaunchServices launch
---------------------------------------------------
Files: fdprobe.c, FdProbe-Info.plist, fdprobe-run.txt, fdprobe-stderr-direct.txt,
fdprobe-stderr-open.txt, stderr-marker-requery.txt.
FdProbe.app is a bundle with fdprobe as its executable, ad-hoc signed. It was
unregistered from LaunchServices afterwards with lsregister -u. fdprobe fstat()s
fd 0-2, asks F_GETPATH, compares the result with stat("/dev/null"), writes a marker
to stderr, logs five os_log lines, and prints os_log_type_enabled for info and debug.

  arm                                              fd 2 is                     parent
  ./fdprobe 2>err.txt            (positive control)  err.txt (marker landed)     the shell
  open -W --stderr err2.txt FdProbe.app (control)    err2.txt (marker landed)    ppid=1
  open -W FdProbe.app                                /dev/null (fd 0, 1 too)     ppid=1
  env -i HOME=$HOME open -W FdProbe.app              /dev/null (fd 0, 1 too)     ppid=1

- Three arms ran under ppid 1, the --stderr control among them. Each had
  XPC_SERVICE_NAME=application.dev.baud.fdprobe.<n>.<n>.
- That launchd connected fd 0-2 to /dev/null is inferred from ppid 1 and from
  launchd.plist(5).
- `open` passed the shell's environment through. The `env -i` arm had TERM and
  LANG unset.
- The Dock and Finder were NOT probed.
- Every arm printed info_enabled=1 debug_enabled=0: Debug is disabled here.
- stderr-marker-requery.txt (12:57, read-only): the stderr markers appear in no
  unified-log query. The same probes' os_log default lines and the NSLog line are
  listed as the positive control. The file also shows the first session's own
  marker queries, as log(1) recorded them.

5. syslog(3)
------------
Files: syslogprobe.c, syslogprobe1.txt (11:21:37; query in log-invocations.txt),
syslogprobe1-reread.txt (12:59), syslogprobe2.c, syslogprobe2.txt (12:05:14, with
stderr sizes), syslogprobe2-syntax.txt (clang -fsyntax-only, 12:57).

Through the SDK's `syslog`, which binds _syslog$DARWIN_EXTSN:
- LOG_CRIT, LOG_ALERT, LOG_ERR, LOG_WARNING and LOG_NOTICE land as Default ("Df").
- LOG_INFO lands as Info ("I"), in syslogprobe1.txt.
- LOG_DEBUG is not listed, even with --debug.

Through the legacy `_syslog` symbol: LOG_WARNING and LOG_ERR land as Default, and
LOG_INFO as Info.

- A heap string through plain %s is shown in full.
- "%{private}s" and "%{public}s" in syslog's format come out as "<decode: missing
  data>", so the value is lost. Clang warns that the annotation is "outside of
  os_log()/os_trace()" (syslogprobe2-syntax.txt).
- No line has a subsystem or a category.
- stderr was 0 bytes for both probes.
- LOG_EMERG was not sent. syslog(3) itself says: "A panic condition. This is
  normally broadcast to all users."

7. The persisted length of a long line
--------------------------------------
Files: capprobe.c, capprobe-reread.txt (12:04:42), capprobe2.c, capprobe2.txt
(12:05:02), lifeprobe.txt (12:36:28).

capprobe.c (11:26:01) logs 600 bytes of %{public}s through os_log_with_type at
ERROR, DEFAULT and FAULT. That route goes through _os_log_impl, not the macros
os_log_error and os_log_fault.
- Re-read at 12:04: 617, 619 and 617 bytes, all 600 'y' kept.

capprobe2.c (12:05:02) logs the same through the documented macros os_log_error,
os_log_fault and os_log_info.
- Read immediately: 622, 622 and 621 bytes, all 600 'z' kept.
- At 12:36:28 the Error and Fault lines were still 622 bytes each. The Info line
  was gone.

log.h caps "written to the persistence store" content at 256 bytes for these
types. It also says "Live streams will continue to show the full content".
- For Error and Fault, the probe reads the persistence store: 600 bytes held
  half an hour on.
- For Info, the only reading that listed the line was taken at once, so it may
  not have come from the store, and the line was gone by 12:15. Debug was never
  emitted. So the probe cannot reach the cap for Info or Debug.
