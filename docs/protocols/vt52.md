# VT52

DEC's 1975 terminal, and the one protocol here that is **not** an ancestor of
the others in a way you can ignore. Reached only by DECANM.

- **Implementation:** `baud-core/src/vt52.rs`, `baud-domain/src/vt/vt52.rs`
- **Tests:** `baud-core/tests/vt52/`, and the VT52 fixture in
  `baud-core/tests/golden/fixtures.txt`, whose rendering is pinned against what
  `baud-core2` produced for it before that crate was deleted -- no recording contains a VT52 byte, so
  the differential fixture is the only thing that can see the sub-graph
- **Conformance:** `vt52` terminfo profile, 17 output capabilities
- **Source:** `[[source: vt510-decanm]]` (Table 5-1), `[[source: ctlseqs]]`
  ("VT52 Mode")

## Why it is a mode and not a subset

The same bytes mean different things:

| byte | ANSI | VT52 |
|---|---|---|
| `ESC D` | IND — down one line, column kept | cursor **left** |
| `ESC H` | HTS — set a tab stop | cursor **home** |
| `ESC J` | *(not an ESC sequence)* | erase to end of screen |
| `ESC K` | *(not an ESC sequence)* | erase to end of line |

A parser serving both from one table is necessarily wrong for one of them. So
VT52 is a disjoint sub-graph of the parser's table, entered at its own ground
node, `Node::Vt52Ground` (`baud-core/src/graph.rs`): no ANSI sequence is
recognised from it until `ESC <` leads back, and the byte loop tests no mode
flag. On `baud-core2` that gate, read
as a flag in the byte loop, measured 4% of the cells path.

## The sequence set

`ESC A B C D` cursor; `ESC F G` graphics mode; `ESC H` home; `ESC I` reverse
line feed; `ESC J K` erase; `ESC Y row col` direct address; `ESC Z` identify;
`ESC = >` keypad; `ESC <` exit, to Level 1 and seven-bit C1 (`[[source:
dec-std-070]]` 070-0A EXIT VT52 EMULATION MODE, p. A-15; the DECSCL row).

## `ESC [` is not CSI here

xterm's "VT52 Mode" table contains no CSI at all, and neither does baud's
implementation. Allowing one would invent a hybrid terminal that never existed
and that nothing targets.

**The cost is real and worth stating.** The only ways out of VT52 are `ESC <`
and a host-side reset. A program that enters VT52 and dies leaves the terminal
there, and `reset(1)` does not rescue it, because `reset` sends `ESC c` and
`ESC c` is not a VT52 sequence. That is how the hardware behaved.

## `ESC Y` — a source conflict, resolved

`[[source: vt510-decanm]]` Table 5-1 describes `ESC Y Pn` as "Move cursor to
column Pn" — **one** operand. `[[source: ctlseqs]]` gives `ESC Y Ps Ps`, "Move
the cursor to given row and column", with "Each ordinate ... encoded in a single
character as value+32" and "The screen coordinate system is 0-based". The
terminfo entry agrees with ctlseqs: `cup=\EY%p1%' '%+%c%p2%' '%+%c`.

baud follows ctlseqs and terminfo. The VT510 line reads as an abbreviation
rather than a different protocol, but both are recorded here because the
disagreement is real.

## `ESC Z` — which identity

`[[source: ctlseqs]]` gives two answers: `ESC / Z` ("I am a VT52 emulated by
VT100") or `ESC / K` ("I am a VT52"), depending on xterm's `decTerminalID`.
baud answers `ESC / Z`, which is what it is — a VT100-family terminal in VT52
mode, not a VT52.

## Declined

The print functions — `ESC ^`, `ESC _`, `ESC W`, `ESC X`, `ESC ]`, `ESC V`.
There is no printer. They are recognised and counted in
`Term::vt52_unsupported`, not silently swallowed.
