# VT220 / VT320

What VT100 applications do not need but real ones do.

- **Implementation:** `crates/baud-core/src/{dcs,write,ops}.rs`
- **Tests:** `crates/baud-core/tests/vt220/`
- **Sources:** `[[source: vt510-decsca]]`, `[[source: vt510-decsed]]`,
  `[[source: vt510-decsel]]`, `[[source: vt510-decstr]]`, `[[source: ctlseqs]]`

## Selective erase is three sequences, not one

DECSCA marks characters unerasable; DECSED and DECSEL are the erases that
honour the mark. Implementing the erases without the protection makes them
silent aliases for ED and EL.

Protection is **not** an SGR attribute — `[[source: vt510-decsca]]`: "DECSCA
does not effect visual character attributes set by the select graphic rendition
(SGR) function" — and it is **not** in the style table either. It lives in
`CellFlags`, per cell (`CellFlags::PROTECTED`). The style table is bounded and,
once every slot is filled, evicts; a cell still naming the evicted slot takes
the new occupant's rendition. Protection stored there would answer from
whichever rendition displaced the original -- core2's 64-slot table did, after
a truecolour application had cycled through enough of them.

The blank an erase leaves behind does **not** inherit protection, or the first
DECSEL under `DECSCA 1` would protect everything it had just cleared.

## DECRQM's interesting answer is the negative one

`[[source: ctlseqs]]` gives `0` as "not recognized", and baud returns it for
every mode it does not implement. That is correct rather than a fallback: an
application uses DECRQM to *discover* whether a mode exists, so replying `2`
("reset") would tell it the mode is available and off, and it would set the
mode and believe it took effect.

## DECRQSS: 1 is valid, and the DEC manuals disagree

`[[source: ctlseqs]]` records the errata directly — "testing a DEC VT420 in 1996
showed that the documented code for a valid or invalid response to DECRQSS was
reversed" — with vttest and DEC STD 070 agreeing against the VT420 and VT525
manuals. baud follows xterm. There is a test named for it, because a reader
consulting the DEC manual would "fix" this in exactly the wrong direction.

## DCS payloads are consumed, never executed

An unhandled DCS reads to its terminator and discards. The guarantee is precise
and narrower than it looks: `[[source: williams]]` says a bare `ESC` *cancels* a
control string, so what is promised is that a payload containing no `ESC` is
inert. Two tests asserted the stronger, wrong version first.
