# baud — input coverage

What baud must **send**, enumerated against primary sources, in the same shape
as `vt-coverage.md` does for what it receives.

The base layer is done: `Term::key` encodes the cursor keys, Home/End, the
editing keys, F1-F20, the text keys, the keypad and the VT52 tables, in both
DECCKM and both DECKPAM modes, with modifiers and in both input encodings.
**Both negotiated layers are done too.** `[[source: fixterms]]`'s `CSI u` is
reachable through `modifyOtherKeys`/`formatOtherKeys` (the base layer's
resources), and `[[source: kitty-keyboard]]`'s progressive enhancement is
encoded in full: all five flags, the per-screen stack, and the `CSI ? u`
query answered, which is the protocol's support claim.
`vt-coverage.md`'s rule is that a row
marked **done** carries a test, and a row marked `partial`
is an operation whose gap is named.
One row carries `**partial**`: find in the scrollback.
A `todo` row here has neither because it has no code.

## Why this file is not a section of `vt-coverage.md`

The output side has one specification to enumerate against. The input side has
three layers, and a row is meaningless without saying which one it belongs to:

| layer | source | what it is |
|---|---|---|
| base | `[[source: ctlseqs]]` | what every terminal sends. Cursor, editing, function and keypad keys, the `CSI 1 ; modifier <final>` form, and `modifyOtherKeys` |
| CSI-u | `[[source: fixterms]]` | `CSI unicode-key ; modifiers u`, a *proposal* to remove the base's ambiguities. **It defines no negotiation**, which is why it is not independently implementable: a terminal that simply started sending it would break every application that had not asked. baud reaches it through the base layer's `formatOtherKeys`, and the rows below carry it |
| kitty | `[[source: kitty-keyboard]]` | progressive enhancement over CSI-u: `CSI > flags u` to push, `CSI < u` to pop, with event types, alternate keys and associated text |

An application asks for the layer it can parse, which is the same shape DECRQM
gives the output side. Confusing them is how a terminal comes to send a
sequence nothing asked for.

## The key tables are extracted, not transcribed

`key_tables` in `baud-core/tests/coverage.rs` reads the ten tables out of
`[[source: ctlseqs]]` -- **112 key rows** -- and `print_the_key_tables`
prints them with the line each was found at. A key table written from
memory is exactly the "guessed table that would be unrecoverable and would
look like it worked" this project refused for DEC line drawing, so it is
generated and re-runnable rather than pasted.

`[[source: kitty-keyboard]]`'s "Functional key definitions" table -- **111
rows** mapping a key name to the number and final byte its `CSI` form uses,
from `ESCAPE = 27 u` through `ISO_LEVEL5_SHIFT = 57454 u` -- and its 35
legacy C0 cells are extracted the same way, from the page's source at kitty
v0.49.2 (`[[source: kitty-keyboard-rst]]`), fetched by URL and refused unless
it hashed to the manifest's SHA-256. The two tables are pinned as baud's own
data, `[[source: kitty-functional-keys]]` and `[[source: kitty-legacy-c0]]`,
each with its own SHA-256 and the parent's on its first line, and the tests
read them without fetching. The tests carry positive controls (`ESCAPE`,
`CAPS_LOCK` and `ISO_LEVEL5_SHIFT` at known values, Alt-Backspace, and the
exact row and cell counts) so a broken extraction fails loudly rather than
reporting a plausible subset. `[[source: kitty-functional-keys]]` is the
source of truth the kitty encoder's
functional-key table is gated against, the way the base rows above are gated
against `key_tables`. ~~The encoder that consumes it is not built yet.~~
It is built, and three tests in `baud-core/tests/kitty_encode.rs` read the
table: `functional_keys_match_the_source` (Esc, Enter, Tab, Backspace, the
arrows, the editing keys and F1-F20), `keypad_keys_match_the_source` (the
digits, operators and `KP_LEFT` to `KP_BEGIN`) and `pua_keys_match_the_source`
(the locks, F21-F35, the media and modifier keys). A fourth,
`every_row_of_the_table_is_gated`, requires the names those three map to be
exactly the table's rows: the navigation rows sat ungated while the
protocol was called complete, because each test named its own keys and none
asked which rows no test named.

## Modifiers

`[[source: ctlseqs]]` line 2565 onward: the parameter is `1 + bitmask`, with
Shift 1, Alt 2, Control 4, Meta 8 -- so shift-F5 is `CSI 1 5 ; 2 ~`. Meta only
appears when `alwaysUseMods` is set, which makes 9 through 16 reachable.

Encoding a modifier is not the same as *having* one. Whether Alt or Meta
prefixes `ESC` or sets the high bit is a pair of resources in xterm, and the
table at line 2337 gives all sixteen combinations across three modes:

| mode | resource | what it does | baud |
|---|---|---|---|
| `?1036` | `metaSendsEscape` | Meta prefixes `ESC` | **done**, and **set** at power-on |
| `?1039` | `altSendsEscape` | Alt prefixes `ESC` | **done**, and **set** at power-on |
| `?1034` | `eightBitInput` | Alt/Meta add 128 instead | **done**, applied under ISO 8859-1 only |

**Option-Backspace deletes a word in a shell**, since 2026-10-19: the
three modes reach Return, Tab, Backspace and Escape as they reach a
character, so with `?1039` set Alt-Backspace sends `ESC DEL` where it sent
a bare DEL, Alt-Return `ESC CR`, Alt-Tab `ESC TAB`, Alt-Escape `ESC ESC` and
Alt-Shift-Tab `ESC CSI Z`. xterm sends those keys down its text branch
(`[[source: xterm-input-c]]`, `kd.nbytes > 0`), and every cell of
`[[source: kitty-keyboard]]`'s legacy table for them is held by
`alt_prefixes_the_c0_keys_as_it_prefixes_text`.

**The defaults are baud's choice and this is where it is recorded.**
`[[source: ctlseqs]]` documents all three and states no default for any of them,
so following it alone would leave the question open. `[[source: foot-meta-defaults]]`
answers it — `meta.esc_prefix = true` in both foot's constructor and its reset
path — and baud follows, because the alternative cannot work under UTF-8: a byte
above 127 is a continuation byte there rather than a character. Same shape as
DECAWM, where the VT510 manual and xterm disagree and `vt-coverage.md` records
which baud follows.

`?1034` is implemented rather than refused because terminfo reaches it: `smm`
and `rmm` are `CSI ? 1034 h` / `l` in every `xterm*` entry, and
`tests/conformance` counted them as recognised-and-dropped for as long as they
were. It is applied only under ISO 8859-1, where a byte above 127 *is* a
character. Under UTF-8 the mode is recorded and reported truthfully and the
shift does not happen — which is a condition on acting, like DECAWM's on the
margin, not a bit set and never read.

**All three were one bit under one number.** `?1034` was mapped to what is
actually `?1036`'s behaviour, so an application asking DECRQM which of the two
opposite branches was in force got the same answer for both, and `?1039` did not
exist. Nothing could detect it while no encoder read the bit; writing one turned
a dormant misnumbering into a wrong answer, which is how it was found.

## The keyboards `?1050` to `?1061`

**A program written for another terminal's keyboard can ask for it**, since
2026-11-01: six private modes each swap the keyboard for one of xterm's
others, "Set terminfo/termcap function-key mode", "Set Sun function-key
mode", "Set HP function-key mode", "Set SCO function-key mode", "Set legacy
keyboard emulation, i.e, X11R6" and "Set VT220 keyboard emulation"
(`[[source: ctlseqs]]` 1032-1039). One is in force at a time: DECSET selects
it, and DECRST of any of the six returns to the default keyboard, the one the
tables above describe, as xterm's `set_keyboard_type()` stores its default
for any reset (`[[source: xterm-scroll]]`'s file, util.c 6077-6093); DECRQM
answers set for the one in force alone (`[[source: xterm-misc]]` 5723-5747).
**XTSAVE and XTRESTORE keep the six as one value**, a keyboard, whichever of
them is listed, as xterm keeps them in `DP_KEYBOARD_TYPE` (`[[source:
xterm-reset]]` 8279-8300, 8734-8756); a family never saved restores the
power-on keyboard, the default one (since 2026-11-03).
`RIS` returns to the default keyboard and `DECSTR` keeps it: its table names
no keyboard (`[[source: vt510-decstr]]`), and xterm resets it in `RIS` alone
(14451-14455). DECTSR carries all six and DECRSTS restores them. **A key a
keyboard does not name sends what it sends on the default keyboard.** At
DECSCL Level 1 the keyboard is a VT100's and in VT52 mode a VT52's whatever is
selected, the mode kept: Level 1 "Shall neither implement additional keys"
(`[[source: dec-std-070]]` 070-6 §6.2.1 b) and "A VT52 does not have function
keys". The kitty layers report keys as they always do, and a resource at 4
takes its keys first, as xterm's `Input()` checks it first
(`[[source: xterm-input-c]]`). `the_keyboards_are_one_family_and_any_reset_returns_to_the_default`,
`xtsave_keeps_the_keyboard_family_as_one_value`,
`ris_returns_to_the_default_keyboard_and_decstr_keeps_it`,
`decrsts_restores_the_keyboard`, `level_one_and_vt52_keep_their_own_keyboards`.

**`?1037` answers what Delete sends.** It keeps xterm's three states: neither
set nor reset, the keyboard decides, `CSI 3 ~` on the default and VT220
keyboards and DEL on the legacy one. DECRQM answers set exactly when the
editing keypad's Delete sends DEL: under the SCO keyboard, whose table sends
DEL, and reset under the termcap, Sun and HP keyboards, whose tables send
`CSI 3 ~`, `CSI 3 z` and `ESC P`. xterm answers its `xtermDeleteIsDEL()`
there, set on all four (`[[source: xterm-misc]]` 5690-5692), which is not
followed (`the_sun_delete_is_its_own_and_1037_answers_what_is_sent`).
**XTSAVE and DECTSR keep what DECRQM answers**, so a restore brings back set
or reset and never the unset state; under the termcap, Sun and HP keyboards a
set `?1037` is saved as reset, and under the SCO keyboard a reset one as set.
xterm saves its three-state value, `DP_DELETE_IS_DEL` (`[[source: xterm-reset]]`
8256), a difference recorded and open
(`xtsave_and_dectsr_keep_1037_as_decrqm_answers_it`).

sends there. baud sends xterm's (`TERM=xterm-256color`), and of the ten
pinned profiles it sends 139 of `xterm`'s 140 input capabilities, all 22 of
`vt100`'s, 38 of `rxvt`'s 99, 43 of `nsterm`'s 45, 26 of `dtterm`'s 32
and 7 of `ansi`'s 8, each profile's `smkx` modes included and the mouse
report `kmous` prefixes counted. Every one it does not send is named below
with the reason; `the_unsent_input_capabilities_are_named` requires this

## Not in scope yet, and why

* **DECUDK** — user-defined keys. ~~It stops being out once there is an
  input side.~~ There is one, and `vt-coverage.md` keeps DECUDK `out` on
  scope rather than on absence: it redefines what a key sends, which needs a
  table of user-programmable strings and a policy for who may set them.
* **~~Compose, dead keys, IME -- these belong to the platform layer above
  baud's core.~~** They do, and the platform layer has them now: the macOS
  app through AppKit's input manager, and since 2026-10-21 the Linux
  driver's Compose sequences and dead keys and its input method through
  `text-input-v3` (the key table's rows).
* **Key repeat is the platform's to generate and the core's to encode.** An
  embedder delivers a held key as `KeyEventKind::Repeat`, and the encoder sends
  it as the press everywhere but `[[source: kitty-keyboard]]`'s event types,
  which report it as `:2`: "Normally only key press events are reported and
  key repeat events are treated as key press events." A release sends nothing
  outside event types. `baud-app` on macOS delivers AppKit's repeats, and
  `baud-present-wayland` repeats a held key itself, as Wayland leaves it to
  the client. Both deliver releases. `?8` DECARM is set at power-on, and
  `Term::key` drops a repeat while an application has reset it.
* **A key's release on Linux reaches the program exactly when its press
  did**, since 2026-10-30. It names the key its press named, as kitty's
  layer names it (`[[source: kitty-glfw-input-c-6d5d0c4]]`), so Shift
  pressed while `q` is held lets go of `q`. A key pressed before the find
  field opened and let go inside it is let go to the program, where the
  release was lost; Escape pressed into the field to close it releases
  nothing after, where the program was told of a key going up it never saw
  go down; and a key already down when the window took the keyboard
  releases nothing (`a_release_goes_to_the_program_exactly_when_its_press_did`,
  `a_release_names_its_press_and_follows_only_a_press_sent`). foot drops
  a release while its search is open and sends the one after it closes
  (`[[source: foot-152487e-input]]`). Repeats go where they went, and the
  find field types what it typed.
* **A key's release on macOS names the key its press named, and goes only
  where the press went**: a Command chord is the menu's, and a key taken
  into a composition, a dead key or a key typed into the find field
  reached no program, so its release is dropped, as is a second one; a key
  pressed before the find field opened and let go inside it is let go to
  the program, as on Linux (`a_key_release_reaches_the_core_as_its_press_let_go`,
  `a_release_without_its_press_or_a_second_one_sends_nothing`,
  `a_dead_key_and_the_letter_it_composes_release_nothing`), as kitty
  pairs them (`[[source: kitty-glfw-input-c-851cb80]]`). A key the input
  manager types is its press, in the window crate's own order: the
  composition ended, empty, before every commit leaves the key, and only
  a composition that is something drops it, while a commit after its key
  came up, the character palette's, is no key's
  (`a_typed_key_is_released_in_the_window_crates_order`,
  `a_commit_after_its_key_came_up_is_no_keys`). So Shift+a is
  `CSI 97;2u` going down and `CSI 97;2:3u` coming up under "report all
  keys" with event types, the key Shift is on both times
  (`a_shift_letters_press_and_release_name_one_key`). AppKit keeps a
  key-up from the view while Command is held, so a key let go after
  Command went down would never be released; one event monitor a window
  hands those to the view, as Ghostty's and kitty's do
  (`[[source: ghostty-d9840f3-surfaceview-appkit]]`,
  `[[source: kitty-glfw-cocoa-init-851cb80]]`;
  `only_a_command_key_up_in_our_window_is_forwarded`,
  `the_command_key_up_monitor_follows_the_responder`), and removes it when
  the window closes. A modifier key pressed or released alone is kitty's
  functional key under "report all keys", Command as super and Option as
  alt, `fn` none, as kitty's macOS layer reports them
  (`[[source: kitty-glfw-cocoa-window-851cb80]]`;
  `a_modifier_key_alone_reaches_the_core_under_report_all_keys`); a
  modifier key pressed while the find field is open goes nowhere
  (`a_modifier_key_pressed_into_the_find_field_sends_nothing`), and an
  input method's commit of more than one character records no key, so no
  release follows it (`a_commit_of_more_than_one_character_records_no_press`).
  A release and a modifier key carry Caps Lock's bit while the lock is on,
  read from the event's own flags as a press's is: "if ... the lock (for
  caps lock/num lock) is enabled, the key event must have the bit for that
  modifier set" (`[[source: kitty-keyboard]]`), so Shift pressed alone with
  the lock on is `CSI 57441;66u` and `a` let go `CSI 97;65:3u`
  (`caps_lock_rides_a_release_and_a_modifier_key`).
* **The keys still down when the window loses the keyboard are let go
  then**, since 2026-10-30, under kitty's event types: after
  `wl_keyboard.leave`, which leaves no key down (`[[source: wayland]]`), the
  compositor sends the window none of their releases, so a game holding `w`
  walked on for good. Only keys whose press the program was sent are let go,
  each once, with no modifier held, before the focus report
  (`the_keys_down_when_the_keyboard_leaves_are_let_go_once`). Ghostty
  releases them too (`[[source: ghostty-d9840f3-surface]]`); kitty builds the
  releases and drops them before the program
  (`[[source: kitty-glfw-window-c-6d5d0c4]]`,
  `[[source: kitty-glfw-c-6d5d0c4]]`), and foot sends none.
  The macOS app lets them go the same way when it sees the window lose the
  keyboard, each with Caps Lock's bit while the lock is on, as kitty asks
  of every key event, read from the last key event the window was handed,
  the lock's own turns among them: Command let go with the lock on is
  `CSI 57444;65:3u` under "report all keys" with event types
  (`the_keys_held_when_the_window_loses_the_keyboard_are_let_go`,
  `a_focus_lost_lets_go_of_the_keys_held`). **Open:** it sees that at its
  next display-link frame or mouse event, and its display link may not
  tick while the window is covered, so a switch to a window that covers
  baud entirely may leave a key held, Command among them, until baud is
  uncovered, and the lock its releases carry is the one the window last
  saw; whether and how often that happens is unmeasured.
* **A Mac's number pad is a keypad.** Its keys are named by key code, not
  by `NSEventModifierFlagNumericPad`, which AppKit also sets on the arrows,
  and each carries the text it types, as on Linux, so kitty's disambiguate
  flag keeps a typed digit a digit. A Mac keypad has no NumLock state:
  no NumLock is reported, so `?1035` changes nothing there and DECKPAM
  always reaches the digits. Clear, the key where a PC keypad has NumLock,
  is NumLock: the HID tables name the one key "Keypad Num Lock and Clear"
  (`[[source: usb-hid-usage-tables-1-6]]`, usage 0x53) and kitty's macOS
  layer names it `NUM_LOCK` (`[[source: kitty-glfw-cocoa-window-851cb80]]`),
  over iTerm2's `ESC` (`[[source: iterm2-7ce037e-standard-key-mapper]]`)
  and its kitty mapper's `KP_SEPARATOR`, "a blind guess" (`[[source: iterm2-7ce037e-modern-key-mapper]]`). It sends
  nothing outside kitty's "report all keys", as before. A keypad key is
  drawn ahead of the echo only from the numeric column.
* **A keypad key types what the layout puts on it.** From the numeric
  column, and under kitty's disambiguate flag, a keypad key sends the
  character it typed, which is its label on a US layout and not on every
  layout: a Mac's decimal key types `,` on German and French layouts and
  its digits type Arabic-Indic digits on Arabic ones. A decimal key that
  types `,` is the keypad's comma, line 2498's `SS3 l` under DECKPAM and
  kitty's `KP_SEPARATOR`, as xkeyboard-config makes a German Linux
  keypad's (`[[source: xkeyboard-config-kpdl-193cc6c]]`), where kitty's
  and iTerm2's macOS layers keep `KP_DECIMAL` (`a_keypad_key_sends_what_it_types_from_the_numeric_column`,
  `a_mac_keypad_key_sends_what_the_layout_types_on_it`).
